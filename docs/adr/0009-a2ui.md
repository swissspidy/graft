# ADR 0009: A2UI surfaces as a build's UI

- Status: Accepted (WordPress and EmDash)
- Date: 2026-10-08
- Builds on: [ADR 0001](0001-architecture.md), [ADR 0006](0006-interactive-widgets.md)
- Supersedes: [ADR 0005](0005-sandboxed-functions.md), [ADR 0006](0006-interactive-widgets.md), and the widget inputs of [ADR 0007](0007-editorial-tools.md)

## Context

A build's UI is a Graft tree: host components, and an expression language
for bindings, permissions and actions. When a tree cannot express
something, it takes code: `$fn` (ADR 0005) or a widget with render and
update functions (ADR 0006), run in the host's sandbox.

[A2UI](https://a2ui.org/) is a published protocol for generated UIs:
- a flat list of components drawn from a catalog;
- a data model, bound with JSON Pointers;
- client-side functions;
- action events.

It was made for agents streaming UIs to clients. Graft's customizations are
permanent mini-apps, compiled once and verified against frozen checks,
with no agent at run time. The question was whether A2UI can carry
Graft's UI without giving up anything else in Graft: specs, checks,
gateway, grants, verification and upgrades.

## Decision

### A build's UI is an A2UI surface

A build has a `ui` with `events` (at first, next to trees; see "Trees are
gone" below):

```json
{
  "ui": { "protocol": "a2ui/v0.9", "catalogId": "graft:wordpress", "components": [/* … */], "initial": {}, "computed": {} },
  "events": { "approve": { "call": "posts.update_status", "input": { "id": { "$context": "id" }, "status": "publish" }, "then": ["remove-row:queue"] } }
}
```

The envelope does not change: spec, mount, data sources, checks, refs and
provenance. An A2UI action is a named event. `events` binds each name to
a capability call. `{"$context": "<key>"}` in the
input stands for the event's resolved context. No agent runs: the Graft
runtime plays the A2UI server. It fills the data model from the data
sources and answers each event with the capability call it is bound to,
through the gateway.

Data sources and event bindings stay in Graft's expression language
(`$slot`, `$context`). They belong to the envelope, which the gateway
enforces, not to the UI.

### Core knows formats only through an interface

Core does not depend on A2UI. A `UiFormat` (`build/format.ts`), registered
per host, covers each place the UI is read:
- **Validation:** the UI against its catalog and the surface.
- **Refs:** what the UI calls and checks, plus its catalog usage
  (`refs.catalog`).
- **Snapshots:** the UI drawn for the verifier.
- **Host migrations:** renames applied to the UI.
- **Re-anchoring:** the slot props the UI reads.
- **Compiling:** the compiler's UI phase.

The schema requires `ui` and `events`. A build with no registered format
to read it is refused.

`@swissspidy/graft-a2ui` implements the format on `@a2ui/web_core` (Apache-2.0).
Verification resolves values with A2UI's own data model and resolver,
not a reimplementation.

### The Graft catalog

A2UI's basic catalog cannot hide a component or branch on a value. The
`graft:<host>` catalogs add what Graft needs; each needed a spec to show
it was missing:

| Addition | Why |
| --- | --- |
| `visible` on every component | Permissions and steps hide things |
| `if`, comparisons, arithmetic | No conditional in A2UI |
| `can` | The host's permission check; in a row it refines on the row's post |
| strings, `count`, `join`, `daysSince` | Checklists, verdicts, ages, without code |
| `filter`, `map`, `distinct`, `sort`, `slice` | Lists derived from data (author buttons, filtered rows) |
| `set` (a local action) | State: which author or post is chosen, which step |
| `computed` | Derived lists live in the data model, since templates and tables only bind to pointers |
| `actionId` on Button | Template-drawn buttons get the ids checks name (`author-ada`) |
| Table | Not in the basic catalog; drawn by the host's own table |

Every component and function argument has a zod schema. A wrong prop or
argument is caught before anything runs, with a message the compiler
sends back to the model.

Every pointer is a JSON Pointer, Table field ids included (`author/name`).
Before that change, Claude wrote `can.publish` in one binding.

### New builds are A2UI surfaces

A host's compiler guide names the format new builds are compiled in
(`HostGuide.ui`); WordPress and EmDash name A2UI. The compiler takes the
caller's format, else the previous build's, else the host's, so:

- writing a customization in wp-admin or the EmDash admin builds an A2UI
  surface, with no change to either authoring flow;
- `graft compile` does too;
- regenerating a build keeps its format; a tree, while trees existed,
  was regenerated in the host's format.

### Trees move over by regeneration

Every build in the repository is an A2UI surface: the examples, the
agency site and the canary corpora. A tree moves over the way the
upgrade ladder already rebuilds a customization: regenerated from its
spec and frozen checks, in the host's format. The canary corpus's
`editorial-inbox`, a tree with no A2UI version, moved that way on its
first attempt. Its provenance records `regenerated` and the tree it
replaces.

### Trees are gone

With every build an A2UI surface, the tree path was removed rather than
kept as a second format to maintain:

- the `tree` field, the hosts' tree components (`components` in
  surfaces) and slot `accepts`;
- build functions (`$fn`, `code`, `@graft/sandbox` and QuickJS) and
  widgets, with the surfaces' `functions` limits;
- the tree-only expressions (`$field`, `$call`, `$input`, `$fn`); data
  source inputs keep `$data`, `$slot`, `$can`, logic, `$if` and
  `$daysSince`;
- component and prop migrations: host migrations rename or remove slots,
  capabilities and scopes; the catalog is versioned by its id.

The surfaces were regenerated, so their hashes changed, and every stored
build was re-stamped. A stored tree no longer validates or serves; it is
regenerated from its spec and checks (`graft compile --previous`), which
builds it in the host's format.

### Hosts draw it their way

- **WordPress:**
  - [a2ui-wp](https://www.npmjs.com/package/@swissspidy/a2ui-wp)'s React
    renderer (`@wordpress/components` on `@a2ui/web_core`) draws through
    `GraftRoot`. It shares the tree's data loading, gateway, `then`,
    notices and the editor's unsaved-changes guard.
  - Its surface uses the verifier's own Graft catalog (`@swissspidy/graft-a2ui/client`),
    so the browser resolves values with the same web_core and functions
    the checks ran on.
  - The Table is Graft's own WordPress table.
  - The renderer is a separate bundle (`build/a2ui.js`, 303 KB, 79 KB
    gzipped, most of it web_core and zod), loaded only on screens that
    serve an A2UI build. `runtime.js` stays at 21 KB.
- **EmDash:**
  - The server renders A2UI to Block Kit through the same walk the
    verifier uses (`walkA2UI` with a drawer).
  - EmDash has no inputs, so its catalog has none.
  - A local `set` is a round trip: its state rides in the buttons'
    values, as widget states do.

## Results

All seven WordPress example specs compile to A2UI against their frozen
checks. All five EmDash examples do too, and none of the builds has code:

| | Tree build needs | A2UI build |
| --- | --- | --- |
| publish-checklist | widget + 50 lines of JS | inputs bound to `/form`, `if`/`formatString`, Publish gated by A2UI Button `checks` |
| pending-by-author | widget + JS | `computed` lists, a template of author buttons with `set` |
| headline-check | `$fn` JS | `join` over `if`/`regex` per rule |
| status-board (EmDash) | widget + JS | `set` + `computed`, state carried in Block Kit button values |

- **End to end in WordPress** (`pnpm test:e2e`): the examples are
  verified, attached and approved through Graft's own paths. They are
  served by the plugin's slots: admin page, Dashboard, block editor
  panel, posts list row actions. waiting-posts is approved by an
  administrator in Tools → Customizations, as for a tree.
- **On EmDash** (`pnpm test:emdash`, `pnpm test:emdash:sandboxed`):
  installed, approved and served through the Block Kit routes, natively
  and in EmDash's plugin sandbox.
  Publish goes through the gateway, a replay by a contributor is refused,
  and the status board switches lists locally. web_core and zod add
  212 KB to the sandboxed plugin (1461 KB → 1673 KB).
- **The agency client site** (`pnpm test:e2e:agency`): both agency
  specs compiled to A2UI on their first attempt. family-friendly needed
  JavaScript as a tree; as A2UI its button is a catalog expression. The
  site's managed bundle, its own approved customization, and the
  in-browser upgrade on Tools → Customizations after the agency changes
  the content model all run on the A2UI builds.
- **Authoring** (`pnpm test:author:emdash`, `pnpm test:e2e`): writing a
  customization in either admin builds an A2UI surface, verified (in
  EmDash's sandbox, natively and sandboxed; in Playground in the
  browser) and approved as before.
- **Upgrades** (`pnpm test:canary`): every synthetic host change
  reaches the outcome the tree builds reach. The exceptions are hosts that
  stop running functions or widgets, which every A2UI build survives.
  Component and prop migrations do not apply: A2UI components belong to
  the catalog, which is versioned on its own (a new catalog id), not by
  host releases.
- **The canary caught a validation mistake.** The A2UI validator refused
  scopes a spec does not request as errors. That duplicated core, which
  checks them through refs and only warns while upgrading, so the candidate
  can exit as needs_approval. Without it, widen-publish-scope failed four
  builds instead of asking for approval.
- **The verifier had a bug that a compile exposed.** A local `set` wrote
  into the build's own `initial` object, so one check's state leaked into
  the next. status-board failed three attempts while Claude chased it.
  Values are now copied into the data model, a regression test covers it,
  and status-board compiles on the first attempt.
- **A two-step flow nobody wrote a tree for**
  (`experiments/a2ui/specs/submit-for-review.md`): the whole compiler,
  checks phase included, produced nine checks.
  - The A2UI build passes them, as a state machine of `computed` values.
    It works out "sent" from the refreshed data, since an event has no
    effect but its call.
  - It shipped a bug the checks cannot see: `initial` chooses post 41,
    hard-coded, so the widget opens at the confirm step wherever post 41
    is a draft. The fixtures never create a post with that id.
  - Checks prove what they cover. The validator now refuses a literal
    start for a pointer that rows write (`a2ui-initial-row-value`). An
    error, not a warning: the compiler sends only errors back. A recompile
    with the same checks passed on its first attempt, starting with
    nothing chosen.

## Consequences

- Builds that needed code no longer do. They survive hosts that stop
  running code, and they do not load the functions sandbox.
- The catalog is now Graft's to design and version. It grows only when a
  spec shows a need. Hosts share the base and differ in what they can
  draw.
- Verification and the browser resolve with the same web_core and the
  same catalog. Before a2ui-wp moved onto web_core, its own resolver
  differed once: it did not resolve bindings inside plain objects, so the
  publish checklist's form showed its binding in the browser while
  passing its checks. The e2e suite caught it, and a unit test covers it.
- Everything here, a2ui-wp included, is Apache-2.0.
- A2UI expressions have no local names. headline-check writes its three
  rules out three times (verdict, any problem, tone).
- Not covered: a data source whose input follows the UI's state, such
  as a search box (also missing for trees).
