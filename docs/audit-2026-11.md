# Audit, November 2026

A full read of the repository, looking for what is broken, inconsistent,
inefficient or no longer needed, and a comparison with
[Extensible Web Apps](https://extensibleweb.app/)
([the article](https://aifoc.us/extensible-web-apps/),
[the code](https://github.com/PaulKinlan/ExtensibleWebApps)).

The first section is what was fixed in the same change. The second is what
was found and left, each with the reason, so it can be picked up one at a
time. The third is the comparison.

## Fixed

### A viewer could put their own data under a build's actions (EmDash, browser extension)

Both hosts keep a build's local state in the page: a button's value on
EmDash, the content script's memory in the extension. On a click the host
draws the build again from fresh data and that state, and runs the action
the fresh drawing offers. The state was written into the data model by
absolute pointer after the data sources had loaded, so a forged state
(`{"/mine/tasks": [{"id": "t4"}]}`) replaced the loaded rows, and the
action ran for a row the viewer was never shown. The gateway still held
(capability in the build, grant, the host's own permission check), so this
reached nothing the viewer's account could not reach by itself; it did
bypass the build's own filters and `visible` conditions, and the ADRs
promise that the page never names an input.

`walkA2UI` now refuses to write entered values under a data source or
`/slot`, and validation refuses a build that would (`a2ui-input-binding`,
`a2ui-model-key`). A button drawn once per list item now carries its item,
so a click on a list that changed in the meantime finds nothing, where it
used to find the neighbour.

### Validation that could be walked around

- `replace` took any pattern: `(a+)+$` on a 29-character title took four
  seconds in the verifier and the viewer's browser, and `(` threw and took
  the whole surface with it. It follows `regex`'s rules now, and
  `TextField.validationRegexp` too.
- A `can` whose scope was read from data, and `can`, `regex`, `replace`
  inside a `formatString` template, were invisible to validation and to
  the build's refs. They are refused.
- Names every object has (`toString`, `constructor`) passed as a bound
  event, a known capability, scope, slot or trigger event.
- A nested expression in a data source input cost 2^depth to validate and
  overflowed the stack on the engine EmDash and the extension use.
- A check with `{"rows": 1}` ended the whole verification; one with
  `{"text": ..., "rows": ...}` passed on the first key alone.

### WordPress plugin

- An unverified build could replace a verified one in any state but
  `active`, and approval then put it live. A version that became active
  through a verified build for another surface served whatever was stored
  for the current one. Serving (`servable_specs`, `trigger_specs`) now
  requires the build for this surface to have passed.
- A build marked `reanchored` could mount in any slot, in any state, past
  the policy's list of places. Only an upgrade re-anchors now, and the
  policy applies to where the build mounts.
- A trigger ran on the build's schedule, not the spec's: the host's
  minimum interval was only checked on the spec. They must agree.
- `/call` stored any `spec` and `capability` string, of any length, in
  the audit log on every refusal: any signed-in user could flush the log
  and fill the options table.
- Titles came from `get_the_title()`: entity-encoded, texturized, prefixed
  "Private: ". A build that sent a title back saved the encoded one.
- A personal customization was served to whoever stored its latest
  version, not to its owner.
- An event trigger queued before its build changed ran anyway.

### Elsewhere

- `graft build --fix-refs` stamped the new spec hash onto a build that
  was still invalid, hiding that its spec had moved on.
- `graft site pull` wrote files named by ids the site returned
  (`../../x`).
- EmDash: an older version still waiting for approval could be approved
  over a newer live one; a build the store refused left the authoring job
  "running" for good; the e2e server left EmDash running on its port when
  setup failed.
- Extension: a customization withdrawn from a new version of the extension
  stayed installed with its grant; the sandbox accepted inputs the gateway
  refuses; a `204` answer crashed the drift probe.
- WordPress admin: "What is checked" read `the post "X" is undefined` for
  every assertion without a status; upgrading in the browser ignored
  trigger grants; a build or grant file that did not parse counted as
  absent.
- Both canary tests passed when the corpus or the scenario was missing.
- Docs: the README's `graft check` command failed as written, the ADR
  table lacked 0012, counts and file names were stale.
  `experiments/a2ui/promote.ts` wrote to a directory that is gone.
- `pnpm validate:examples` now covers all four example sets.

## Fixed in a second pass

[ADR 0013](adr/0013-operating-and-recovering.md) records the decisions.

- A managed customization's build can be carried over to a new surface,
  not replaced.
- The spec source is stored as written (its own meta), and PHP trims the
  same trailing whitespace as JavaScript when hashing.
- The drift probe derives the observed output from the declared schema:
  what the surface withheld stays out unless a declared key next to it
  is gone, and the result no longer depends on the probe account's data.
  A probe that is signed out stops, and a capability that no longer
  answers is removed from the observed surface.
- CI tests a branch through its pull request only, the nightly canary
  runs weekly, and the demo is published only after `pnpm test:demo`.
- `experiments/a2ui` keeps the one spec an ADR cites; `experiments/kanban`
  is covered by `pnpm check:builds`.
- Borrowed: safe mode, a change log, "Not showing" with its reason,
  locked areas for the browser host. Local state from the page is cut
  down to what the build's own actions set. "Only for me" when writing a
  customization.

## Found, not fixed

Each of these needs a decision, a wider change, or a suite that could not
confirm it here.

### Security and correctness

| Where | What | Why it waits |
| --- | --- | --- |
| `store.php` `attach_build`, `approve_version` | A version can be `active` with nothing to serve for the current surface (activated by a build for another surface; approved after the surface changed). It is not served and the screen now says why ("Not showing"); the state is still `active`. | Lifecycle change: these should go to `upgrading`. |
| `policy.php` `install_managed` | A managed bundle removed and restored can never be installed again (`graft_id_in_use`), and the failed sync re-runs on every request. `graft_managed_report` is written and never read. | Needs a tombstone or re-adoption rule. |
| `triggers.php` trigger state | One option, read and written whole: a pause during a run can be overwritten; state of removed triggers is never pruned. | One option per trigger. |
| `packages/a2ui/src/validate.ts` `schemaProblems` | Drops every schema issue under a binding or call, even where the schema wants a literal. `can` and `replace` are now checked by hand; other literal-only props are not. | Report `invalid_type` at dynamic values; needs a pass over the catalog. |
| `packages/a2ui` `formatString` | Calls inside templates are still not validated (unknown functions, argument types); only the dangerous four are refused. | Parse templates with web_core's expression parser. |
| `packages/core/src/build/validate.ts` | An omitted input is never checked against the capability's input schema, `$data` in a data source input validates but can never resolve, and mount options are not compared with the spec's. | Each changes what existing builds must satisfy. |
| `packages/core/src/verifier/run.ts` | `matchesRecord` falls back to nested objects, so `{id: 3}` matches a row whose author has id 3. The verification record copies the surface hash from the build's own claim. | The first changes how frozen checks match. |
| `packages/core/src/upgrade/ladder.ts` | The regenerate rung trusts the callback to keep the checks frozen. | Compare `candidate.checks` with `build.checks`. |
| `schemas/spec.schema.json` `requires` | Accepted, read nowhere. | Check it or remove it. |
| `hosts/emdash` store | The 25-version cap applies to administrators (WordPress exempts them) and nothing prunes, so a customization stops taking updates. There is no decline route. Local state survives only for the clicked customization on a shared page. | Product decisions. |
| `hosts/chrome-extension` `background.ts` | Customizations are keyed by spec id alone (two apps, or two surfaces of one app, overwrite each other); storage writes are unserialized. | Key change needs a migration of stored data. |
| `hosts/chrome-extension` `http.ts` | A write that answers `204` has happened but is reported as drift and as a failure. | Decide what a write without a body means. |
| `.github/workflows/release.yml` | Every push to `main` between staging and approval stages the same version again. | Could not test npm's behaviour here. |
| Node scripts (`sandbox.ts`, `server.ts` on both hosts) | Playground and EmDash are spawned detached and only `close()` stops them: Ctrl-C or a CI cancel leaves the process and its temp directory. | One shared "kill on exit" helper. |

### Inconsistent

- PHP re-encodes surfaces and model answers through associative arrays, so
  `{}` reaches the browser as `[]` (`runtime.php`, `rest.php`,
  `generate.php`). The builds route already works around it.
- `@wp-playground/cli` is pinned to 3.1.60 and the bundled client is
  3.1.61; the browser sandbox hardcodes PHP 8.3.
- A hidden `Button` is reported as unavailable, a button in a hidden
  container is not reported at all, so `direct` checks cannot name it.
- `$daysSince` uses `Date.parse` in TypeScript and `strtotime` in PHP.
- `packages/core` says Node 22, the repository Node 24.
- ADRs 0003, 0004 and 0008 still describe trees and QuickJS in places;
  ADR 0001 lists a `SpecStore` and a glossary that were never written.
- `docs/compiling-with-claude.md` loops over all nine example specs; the
  run it documents had seven.
- Hand-written builds claim `graft-compiler/0.1.0+a2ui` as their compiler.
- Nothing checks that a change to a published package has a changeset.

### Inefficient

- WordPress: three or more queries per active customization on every
  admin page and every `/call`; `trigger_specs()`, `surface_triggers()`
  and `policy()` are recomputed per call; `current_surface()` parses every
  shipped snapshot on every request.
- EmDash: the spec is parsed again on every request to read its audience;
  the Manage tab lists the store two or three times.
- Extension: every content message re-hashes every installed spec and
  build; the mutation observer scans the whole document while an anchor is
  missing.
- `graft bundle` starts one sandbox per build. The WordPress table
  renderer calls `indexOf(row)` per cell.
- CI bundles the WordPress client three times in one job.

### No longer needed

- Duplicated across hosts: `createCan`, `loadCorpus`, `rowKey`,
  `nextState`, the Anthropic request in `hosts/emdash/.../model.ts` and
  `packages/cli/src/anthropic.ts`, the check runner in three smoke
  scripts, three seed scripts.
- Unused exports of the published packages (removing them is a breaking
  change): from core `specCriterion`, `isExpression`, and the expression
  guards only core uses; from a2ui the zod helpers in `catalog.ts`.
- WordPress client: `table.tsx` still carries props of the tree renderer.
  Extension fixture: four `/__fixture/*` routes nothing calls.
- `@types/jsdom` in `packages/renderer-react`.

## Compared with Extensible Web Apps

Extensible Web Apps is a kernel in the browser: every feature is a plugin,
a plugin is one JavaScript file in its own Worker, and a person, or an
agent for them, adds, edits and removes plugins while the app runs. Graft
answers the same question (how do people who do not write code change
software safely) from the other end: no code at all, and a spec that
outlives the host's next version.

### Where the two agree

- **The manifest is data, read before anything runs.** There, the first
  statement of the module; here, the spec's frontmatter. Permissions are
  the unit of trust, and a gate checks every call against them.
- **Views are data.** There, sanitized HTML with text-only template holes;
  here, a catalog of components. Neither lets a customization script the
  page.
- **The model only sees what it may use.** There, an agent's tools are
  filtered by its manifest; here, `describeSurface` lists only the
  capabilities the spec's permissions cover.
- **Automation is budgeted and observable.** Agent limits (runs per hour,
  tokens per day, steps) there; `maxPerRun`, rate limits, the run log,
  pause and dry run here.
- **Secrets stay out.** There a plugin names a secret and the kernel fills
  it in per host; here model calls go through the host's own AI client or
  secret setting.

### What Graft has that it lacks

The article names four reasons sites avoid customization and leaves the
fourth open: a core update breaks what people made. A plugin's `version`
field is all there is. That is the problem Graft is built around:
surfaces with hashes, frozen checks, the ladder, the canary. Graft also
verifies behaviour before anything goes live; there, a review card shows
code and permissions and a person says yes.

### What to take from it

1. **Mark places `review` and `locked`, not only offer slots.** Its
   `data-extend` lets an app's author say "ask first" or "never" for an
   area, while leaving everything else open. Graft's surface is an
   allowlist of slots; the browser-extension host, which has no slots of
   its own, could carry such marks in the app description so that a
   payment form is never an anchor.
2. **Say when a place stopped matching, where the person looks.** A
   place that matches nothing is shown in its Customize panel. The
   extension host resolves an anchor by selector, then by landmark, and
   proposes only test ids, ids and labelled tags, never positions, which
   is the same ranking its guide gives. But a broken anchor is only in
   the drift log on the options page; the app's page shows nothing.
3. **A way back that needs no admin screen.** `?reset` there turns every
   plugin back on before any runs. Graft has `GRAFT_DISABLE_TRIGGERS` and
   "Pause all" for triggers, and nothing for views: a build that breaks
   Tools → Customizations has to be archived over REST. A
   `GRAFT_SAFE_MODE` constant that serves nothing would cost a few lines.
4. **One log of changes.** It records every install, removal, grant and
   reviewed write. Graft logs gateway refusals (the last 100) and trigger
   runs, and not who approved what and when beyond the grant's
   `approved_by`. An append-only change log per site would make the
   approval trail readable.
5. **Review a write, not only a permission.** Writes to data a plugin does
   not own wait on a card with a diff, with "once" and "always". Graft
   approves scopes up front. For triggers, the first run of a new version
   could be a dry run the administrator confirms, using what dry run
   already computes.
6. **Checkers that can only stop.** `plugins:beforeAdd` lets a plugin or
   an agent veto an install and never approve one. Graft's policy filter
   is the same shape for agencies; a hook between verification and
   approval would let a site add its own checks without touching the
   plugin.
7. **Agents from outside.** It exposes a plugin's tools over MCP and
   WebMCP with the plugin's own permissions. Graft's capabilities are
   already named, typed and scoped: exposing "write a spec, compile,
   verify" as tools would let any agent author customizations without
   Graft owning the chat.

### Where Graft should not follow

- **Code in a Worker.** A Worker with a strict CSP is a good sandbox in a
  browser. Graft's hosts render on servers too (EmDash's Block Kit, PHP),
  and ADR 0009 dropped sandboxed functions for a reason: data can be
  migrated, re-anchored and diffed; code cannot.
- **CSS selectors as the main way in.** Places make every page open by
  default, and a place that matches nothing "draws nothing and says so".
  That is honest, and it is the breakage Graft exists to prevent. Slots
  with a hash stay the default; anchors stay the exception, with drift
  detection, for apps that offer nothing else.
- **Plugins owning data and hooks between plugins.** Collections with
  schemas and `data:changed` events make its demos compose. A
  customization that owns data becomes something the host must migrate,
  and one that listens to another cannot be verified alone. ADR 0006's
  local state is as far as this should go until there is a need the
  criteria cannot express.

### Where Graft got it wrong, seen from there

- **The person using it cannot change anything.** There, anyone adds a
  plugin for themselves. In Graft only administrators wrote specs;
  `scope: user` existed in the store and no client sent it. Fixed since:
  [ADR 0014](adr/0014-customizations-of-ones-own.md) gives everyone who
  can edit posts customizations of their own on WordPress.
- **Local state lived in the page and was trusted.** Its rule is that a
  view's actions go back only to the plugin that drew it, with rights the
  host tracks itself. Graft's server-rendered hosts sent state to the
  client and read it back as truth; the fix here closes the hole, and
  keeping that state on the server (per viewer and customization) would
  remove the class.
- **No trace.** Every message, check and refusal there is recorded and
  shown in a debugger that is itself a plugin. When a Graft customization
  shows nothing, the reason (not servable, not granted, audience, drift)
  is computed and thrown away on WordPress and EmDash; only the extension
  keeps a drift log.
